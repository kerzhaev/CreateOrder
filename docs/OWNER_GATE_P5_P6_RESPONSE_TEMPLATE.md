**P5-Q2. Допустимые события и выплаты**

- Разрешённые `event_type`: `ENROLLMENT, TRANSFER, EXCLUSION`
- Разрешённые `PaymentCode`/виды выплат: `все подтверждённые выплаты сотрудника; конкретные строки не смешивать без одинакового основания`
- Можно ли объединять `ENROLLMENT`, `TRANSFER`, `EXCLUSION` в одном документе: `ДА — отдельный § для каждой присутствующей аналогичной категории; внутри § отдельные подпункты по сотрудникам`

**Уточнение владельца P5-Q2 (30.08.2026):** в одном приказе создаётся отдельный
параграф для каждой фактически присутствующей аналогичной категории событий.
Например, `§1` может содержать зачисления, `§2` — перемещения, `§3` — увольнения;
если присутствует только одна или две категории, создаются только один или два
параграфа. Внутри каждого `§` сотрудники идут отдельными подпунктами с собственным
действием, датами, выплатами и документами-основаниями. Лимит не более 100%
относится к группе надбавки за особые достижения. Водительская надбавка
начисляется сверх этого лимита; 60%-ное основание для контракта после 21.09.2022
также хранится отдельным основанием. Выплаты разных сотрудников никогда не
объединяются и не дедуплицируются.

**P5-Q3. Ключ совместимости**

Для формирования параграфа ключом является только аналогичная категория события
(`event_type`). Совместимость выплат между сотрудниками не применяется: каждая
выплата навсегда остаётся в подпункте своего `EmployeeID`/`EventID`, даже если
совпадают вид, процент и основание.

Поля ниже проверяются у каждой выплаты конкретного сотрудника, но не используются
для объединения выплат разных сотрудников:

- [ ] `PaymentCode`
- [ ] `ActID`/номер НПА
- [ ] `ActPoint`
- [ ] `AmountKind`
- [ ] значение/процент
- [ ] дата начала
- [ ] расчётная база
- [ ] обязательные документы
- [ ] текст основания
- Другое: `________________________________`

**P5-Q4. Несовместимые записи**

- Поведение: `различия выплат не блокируют; выбранная выплата без основания подсвечивается; при такой ошибке общий экспорт блокируется до исправления или снятия выбора`
- Текст предупреждения: `Не указано обязательное основание выплаты: {PaymentCode}. Заполните поле или снимите флажок выплаты.`

**Решение владельца P5-Q4 (30.08.2026):** если выплата включена флажком, но её
обязательное основание не заполнено, соответствующее поле подсвечивается и общий
экспорт не выполняется до исправления либо снятия флажка. Если выплата не
выбрана, её пустые поля не проверяются и выгрузке не мешают. Различия выплат
между сотрудниками не являются ошибкой. Разрешённый итог выше 100% из-за
водительской надбавки показывается как предупреждение, но экспорт не блокирует.

**P5-Q5. Порядок**

- Сортировка параграфов: `по порядку первого появления категории в таблице сохранённых записей`
- Сортировка сотрудников внутри параграфа: `по порядку заведённых записей в таблице`

**P5-Q6. Нумерация**

- Начинать с `§1` в каждом документе: `ДА`
- Другие правила нумерации: `параграфы идут только для фактически присутствующих категорий; подпункты сотрудников внутри каждого § — 1, 2, 3…`

**P5-Q7. Регистрация**

- `DocumentType`: `PERSONNEL_GROUPED_ORDER`
- Статус документа после успешного экспорта: `EXPORTED`
- Основной `DocumentRegistry.EventID`: `первый EventID по порядку документа (legacy-ссылка)`
- Подтверждаю отдельные связи `DocumentEventLinks`: `ДА — по одной строке на каждый включённый EventID с ParagraphNo и Role`

**Уточнение владельца P5-Q7 (30.08.2026):** сначала военнослужащий и его
кадровое событие сохраняются в реестре, затем отдельный макрос выбирает
сохранённые записи и формирует общий приказ. Для совместимости с текущей схемой
выбран `DocumentType=PERSONNEL_GROUPED_ORDER`, успешный документ получает статус
`EXPORTED`, а legacy-поле `DocumentRegistry.EventID` содержит первый `EventID`.
Полный состав событий сохраняется в `DocumentEventLinks`.

- Набор сценариев/образцов для проверки: `оператор просматривает сформированный DOCX; при отсутствии замечаний распечатывает его`
